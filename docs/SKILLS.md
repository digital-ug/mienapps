# MIENAPPS — Скилы Claude Code и дисциплина «написал → проверил → запушил»

> Цель: Claude Code не просто пишет код, а **расследует перед правкой, пишет тесты, проверяет, ревьюит и
> пушит по гейту**. Скилы берём из ECC (https://github.com/affaan-m/ECC), адаптируем под веб-стек MienApps.
> Скилы — это инструменты дисциплины, не магия (RULES §7).

---

## 1. КАКИЕ СКИЛЫ СТАВИМ И ЗАЧЕМ (под наш стек)

| Скил (ECC) | Когда срабатывает | Что даёт MienApps |
|---|---|---|
| **gateguard** | Перед первым Edit/Write/Bash в задаче | Заставляет РАССЛЕДОВАТЬ до правки: прочитать реальный файл и **форму данных** (схему БД, форму JSON от модели, payload вебхука). Лечит главный класс багов — «предположил структуру». |
| **systematic-debugging** | На баг-репорте | Структурный разбор: воспроизвести → сузить → доказать причину. Без гадания. |
| **test-driven-development** (`tdd-workflow`) | Новая фича / фикс / рефактор | Тесты СНАЧАЛА (RED→GREEN). Для нас: unit (Vitest) + e2e (Playwright). Для AI-выхода — **evals** (см. §3). |
| **verification-before-completion** | Перед тем как сказать «готово» | Запрещает «done» без зелёных typecheck/build/unit/eval/e2e. Это наш аналог Maestro-гейта. |
| **requesting-code-review** / **receiving-code-review** | После реализации, до push | Сабагент-ревью diff'а на регрессии/безопасность перед коммитом. |
| **eval-harness** | Любое изменение промпта/модели | Запустить eval-набор и сверить выход (схема/язык/safe_block/бан-лист). |
| **ai-regression-testing** | Изменение промпта/модели | Защита от дрейфа промпта между версиями (выход не должен деградировать). |
| **production-audit** | Перед публикацией нового продукта | Чек готовности: секреты на сервере, TTL загрузок, дисклеймеры, вебхук verify, лимиты. |
| **codebase-onboarding** | Новая сессия / новый продукт | Быстро понять монорепо (где lib, где продукт, где поток). |
| **subagent-driven-development** | Крупная задача | Разбить на под-задачи и делегировать сабагентам (ревью, тесты) параллельно. |
| **brainstorming** | Ранний дизайн продукта | Только на этапе идеи; не в баг-фиксах. |

> Не ставим всё подряд. Эти 12 покрывают наш цикл. Остальные скилы ECC (java/kotlin/pytorch и т.п.) нам не нужны.

## 2. УСТАНОВКА СКИЛОВ (один раз; делает Claude Code по нашему промпту)

Скилы кладутся в репо в `.claude/skills/` (project-level — применяются только к этому репо), плюс правила
стека `rules/typescript` и `rules/common` из ECC. GateGuard — это ещё и hook (`.claude/hooks/`), включается в
`hooks.json`.

> 📋 Промпт для Claude Code (вставит owner):
> «Склонируй https://github.com/affaan-m/ECC во временную папку. Скопируй в наш репо в `.claude/skills/` только
> эти скилы: gateguard, systematic-debugging, tdd-workflow, verification-before-completion, requesting-code-review,
> receiving-code-review, eval-harness, ai-regression-testing, production-audit, codebase-onboarding,
> subagent-driven-development, brainstorming. Скопируй `rules/common` и `rules/typescript` в `.claude/rules/ecc/`.
> Включи GateGuard-hook в `.claude/hooks.json`. Покажи, что включилось. Ничего из продакшен-кода не трогай.»

GateGuard может мешать на сетапе/чинке — тогда сессию начинать с `ECC_GATEGUARD=off` (по доке ECC).

## 3. EVALS — TDD ДЛЯ AI-ВЫХОДА (ключевая адаптация)

Обычный TDD проверяет код. Но продукт MienApps = ВЫХОД ПРОМПТА. Поэтому к TDD добавляется eval-слой:

`tests/eval/<product>/cases.ts` — фиксированные входы (включая кризисный) + ассерты:
- схема JSON валидна и слоты заполнены;
- язык выхода = язык входа;
- кризисный вход → `safe_block:true`;
- бан-лист пуст (диагнозы, реальные фамилии, оскорбления внешности);
- форма/длина в норме.

`npm run test:eval` гоняет это через реальный `pipeline`. **Изменил `prompt.ts` или роутинг — обязан прогнать
evals и приложить результат.** CI блокирует merge при красном eval, если в diff есть `prompt.ts`/`lib/ai`.

## 4. ЖЁСТКАЯ ПОСЛЕДОВАТЕЛЬНОСТЬ ЗАДАЧИ (то, что значит «не просто писать, а проверять и пушить»)

Для КАЖДОГО ТЗ Claude Code идёт строго по шагам (это дублируется в CLAUDE.md как закон):

1. **Прочитать** RULES + PROJECT_CONTEXT + ACTIVE_WORK + сам ТЗ. (codebase-onboarding при необходимости)
2. **gateguard:** расследовать перед правкой — открыть реальные файлы, проверить формы данных (схема БД,
   форма ответа модели, payload вебхука). Не предполагать структуру.
3. **TDD (RED):** написать/расширить тесты + evals, которые сейчас падают.
4. **Реализовать (GREEN):** минимальное изменение, чтобы тесты позеленели. `lib/*` не трогать без причины из ТЗ.
5. **Observability:** добавить Sentry-теги/крошки по секции OBSERVABILITY ТЗ.
6. **verification-before-completion:** прогнать `typecheck` + `build` + `test:unit` + `test:eval` + `test:e2e`.
   Все ЗЕЛЁНЫЕ. Красное = не готово.
7. **Code review:** requesting/receiving-code-review — сабагент-ревью diff'а.
8. **Коммит** в `feature/*` или `dev`. ТЕМ ЖЕ коммитом **обновить ACTIVE_WORK.md**. Push в `dev`.
9. **CI** (Playwright + evals + build) на push → должен быть зелёным = гейт.
10. **Отчёт owner'у:** что изменено, что проверить на staging (клик-by-клик), точный Sentry-запрос/команда для валидации.
11. Owner проверил на staging → ок → Claude Code (по команде) merge `dev→main` = **публикация**.

**Никогда:** не объявлять «готово» без шага 6; не пушить в `main` напрямую; не трогать `lib/*` сверх ТЗ;
не оставлять `console.log` как источник правды (только Sentry).

---

## 5. ГРАНИЦЫ (честно)
- Скилы делают итерацию дисциплинированнее. Они НЕ заменяют диагностику и runtime-проверку на staging.
- GateGuard и ревью ловят класс «предположил/не проверил», но не заменяют evals для качества AI-выхода.
- Авто-починка (Sentinel-lite) — не про код-фиксы; код всегда через ТЗ.
