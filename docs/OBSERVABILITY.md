# MIENAPPS — Observability, Evals & Sentinel-lite

> Назначение: единое место, через которое архитектор (Claude.ai) и owner видят **полное** состояние всех
> продуктов из Sentry; качество AI-выхода защищено evals; проблемы после деплоя ловит Sentinel-lite, а
> регрессии до деплоя — CI-гейт (Playwright + evals). Принцип: **сначала знай состояние — потом реагируй.**
> Перенос модели Sovyra «Sentinel» на веб-стек (Vercel/Sentry вместо Railway).

---

## 1. ПРИНЦИП (два правила, которые легко упустить)
1. **Тишина не должна быть двусмысленной.** Если тихо — это «всё зелёное», а не «монитор умер». Отсюда
   дневная сводка + watchdog (§5).
2. **Авто-починка не должна маскировать поломку.** Бесконечные ретраи прячут смерть. Жёсткий предохранитель:
   одна и та же авто-починка не чаще 3 раз за 6 часов, затем эскалация к owner'у.

---

## 2. SENTRY — ЕДИНАЯ СХЕМА ТЕГОВ (это и есть «видеть всё»)

**Решение (принято, не обсуждается per-TZ):** один Sentry-проект `mienapps-web`, всё фильтруется тегами.
(Отдельные проекты на продукт заводим только если объём станет неуправляемым.)

**Обязательные теги на КАЖДОМ событии:**
| Тег | Значения | Зачем |
|---|---|---|
| `product` | `inner-world-map` / `inner-child-letter` / `future-self-voicemail` / `ai-courtroom` | фильтр по продукту |
| `feature` | `order` / `checkout` / `webhook` / `pipeline` / `artifact` / `email` / `queue` / `client` | где сломалось |
| `path` | `client` / `server` / `worker` | какой слой |
| `tz` | `TASK_ICL_03` и т.п. | какой ТЗ это тронул → можно валидировать фикс запросом |

**В `extra` (не теги — высокая кардинальность):** `order_id`, `model`, `finishReason`, `length`, `costCents`.

**Уровни (важно — иначе реальные сигналы тонут в шуме, как было в Sovyra):**
- `Sentry.captureException(...)` — только реальные краши (pipeline бросил, webhook 500, рендер упал).
- `Sentry.captureMessage(..., "warning")` — деградация без полной поломки (JSON от модели кривой и был
  ретрай; артефакт сгенерён, но пустой; email не ушёл).
- `Sentry.addBreadcrumb(...)` — рутинный lifecycle («pipeline: started», «artifact: rendered»). **НЕ** issue.
  Крошки прицепляются к любому последующему exception в том же запросе → диагностика без чтения кода.

> **Правило выхлопа (как в Sovyra):** per-request успешные lifecycle-события — это breadcrumbs, НЕ
> captureMessage. Иначе на каждый заказ плодится Sentry issue без диагностической ценности и топит сигнал.

**Sample rate:** 1.0 для всего, что трекаем (объёмы пока низкие; экономить нечего).

**Доступ архитектора:** Sentry MCP подключён к Claude.ai owner'а (как в Sovyra). Claude.ai видит продакшен-
ошибки сразу, без скриншотов от owner'а. Vercel logs тоже стянуть в Sentry (stdout сам по себе невидим).

### Типовые запросы для диагностики
- `product:inner-child-letter feature:pipeline` за 24ч — что ломается в генерации письма.
- `tz:TASK_ICL_03 count > 0` — приземлился ли фикс из этого ТЗ.
- `feature:webhook path:server level:error` — проблемы приёма оплаты.

## 3. EVALS — КАЧЕСТВО AI-ВЫХОДА (Maestro-аналог для AI-продуктов)

Продукт = выход промпта. Регрессия здесь — **дрейф промпта**, его ловят НЕ unit-тесты, а **evals**.

**Где:** `tests/eval/<product>/` — набор фиксированных входов + ассерты на выходной JSON.
**Что проверяем (минимум на продукт):**
1. **Схема валидна** — JSON парсится, все обязательные поля на месте, нужные слоты заполнены.
2. **Язык совпадает** — выход на языке ввода (RU вход → RU выход).
3. **Безопасность сработала** — кризисный тест-вход (самоповреждение/абьюз/несовершеннолетние) → `safe_block:true`.
4. **Бан-лист** — в выходе нет запрещённого (диагнозы, реальные фамилии в вердикте, оскорбления внешности).
5. **Длина/форма** — например, письмо 120–180 слов; future-self ≤60 сек озвучки.

**Жёсткое правило:** любое изменение `prompt.ts` или роутинга моделей в `lib/ai` НЕ мёржится в `main` без
зелёного прогона evals. Это записано в CI (§6) и в RULES §5.

**Реализация:** маленький раннер `tests/eval/run.ts` гоняет входы через реальный `pipeline` (или только AI-слой),
печатает PASS/FAIL по каждому ассерту. Дёшево (несколько модельных вызовов). Запускается локально и в CI.

## 4. ЗОЛОТОЙ ПУТЬ (синтетический прогон) + SENTINEL-LITE

Нельзя гонять реальные платные заказы. Поэтому:

**Внутренний тест-эндпоинт** `POST /api/internal/golden-path` (защищён `Bearer ${INTERNAL_SECRET}`):
запускает `pipeline(product)` на фиксированном тест-вводе, **минуя оплату**, и проверяет: артефакт создан +
эмитнута крошка `golden_path: ok`. Если упал — `captureException` с `feature:golden-path`.

**Sentinel-lite** (лёгкий аналог Sovyra-Sentinel, без отдельного сервиса):
- **cron-job.org** дёргает `/api/internal/golden-path` для каждого живого продукта раз в N минут.
- Раз в сутки — `/api/internal/daily-digest`: считает из БД и Sentry ключевые числа и шлёт ОДНО сообщение в
  Telegram owner'у: заказов за сутки, успешных/упавших генераций, статус последнего деплоя, результат золотого
  пути, расход на API. **Тишина = всё зелёное** (потому что дайджест приходит всегда).
- **Watchdog:** отдельный job на cron-job.org дёргает `/api/internal/heartbeat`; если не ответил — этот job
  сам пишет owner'у (сторож сторожа: монитор не может «тихо умереть»).

**Три полосы реакции (правила, не ИИ):**
- **Полоса 1 — авто-починка** (только идемпотентное/неразрушительное/ограниченное/известная сигнатура):
  напр. cron пропустил тик → повторно дёрнуть; транзиентный 429/503 в worker → ретрай с backoff. Лог + в дайджест.
- **Полоса 2 — короткая инструкция owner'у** (нужен клик): по шаблону «что сломалось (просто) → клики → время».
  Пример: «Paddle webhook перестал приходить → зайди в Paddle → Notifications → проверь, что destination Active».
- **Полоса 3 — диагноз за Claude.ai** (новое/код): Telegram «X сломалось, разбираюсь, принесу фикс». Код не трогаем.

**Предохранитель:** одна авто-починка ≤3 раз/6ч, затем → полоса 2. (Прямой урок Sovyra: ретрай прятал смерть cron 8 дней.)

## 5. ЧЕСТНОСТЬ СИСТЕМЫ
1. **Дневная сводка** — приходит всегда (молчание = зелёное, а не «монитор мёртв»).
2. **Watchdog** — внешний job проверяет, что Sentinel-lite жив.
3. **Самотест при деплое** — после каждого деплоя прогнать тестовый алерт по всей цепочке до Telegram.

---

## 6. CI-ГЕЙТ (регрессии ДО деплоя) — `.github/workflows/ci.yml`
На каждый PR в `dev` и перед merge в `main`:
1. `npm run typecheck`
2. `npm run build`
3. `npm run test:unit` (Vitest)
4. `npm run test:eval` (prompt-evals — если в diff есть `prompt.ts`/`lib/ai`)
5. `npm run test:e2e` (Playwright — золотой путь продукта на staging-preview)

**Зелёный CI — это гейт перед merge в `main` (= перед публикацией).** Аналог Maestro-гейта в Sovyra.

## 7. OBSERVABILITY В КАЖДОМ ТЗ (обязательная секция)
```markdown
## OBSERVABILITY (обязательно)
- [ ] Какой Sentry-тег/крошку добавляет это изменение? (точное значение `feature:` и `tz:`)
- [ ] Критерий приёмки как Sentry-запрос ИЛИ Playwright-ассерт ИЛИ eval.
- [ ] Если чисто UI — хотя бы одно client-событие Sentry на взаимодействие с изменённой поверхностью.
- [ ] Никаких console.log как источника правды о проде (Vercel stdout невидим owner'у — только Sentry).
- [ ] Если тронут prompt.ts / lib/ai — указан eval, который это покрывает.
```
Если код меняет видимое поведение — он ОБЯЗАН эмитить Sentry-событие, иначе фикс невозможно валидировать без owner'а.

## 8. ЧЕГО ЭТА СИСТЕМА НЕ ДЕЛАЕТ (честные границы)
- НЕ чинит баги в коде — это всегда полоса 3 → диагноз → ТЗ → Claude Code.
- НЕ заменяет CI-гейт (тот ловит регрессии ДО деплоя; Sentinel-lite — проблемы ПОСЛЕ).
- Авто-починка покрывает малую долю (инфра-ретраи). Ценность — фильтр и перевод на человеческий язык.

## 9. ФАЗЫ ПОСТРОЙКИ (через ТЗ для Claude Code)
- **Фаза 1:** Sentry-инструментация по схеме §2 во всех роутах потока + client. Чистка уровней. (1 ТЗ)
- **Фаза 2:** evals для первого продукта + CI-шаг evals/Playwright. (1 ТЗ)
- **Фаза 3:** `/api/internal/golden-path` + `/daily-digest` + Telegram-бот + watchdog (Sentinel-lite). (1–2 ТЗ)
- **Фаза 4 (постоянно):** монитор расхода API, дрейф версий, расширение каталога авто-починок.
